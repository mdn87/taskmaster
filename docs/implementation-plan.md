## 1. Outcome, scope, and ownership

The first release must let **agents, the morning report, and Dias** inspect the same objective trail. All three ship together. They must agree on identity, recorded links, gap codes, content digests, and observation metadata; comparison tests use the same clock. A CLI-only release is incomplete.

Taskmaster is a separate local project under `MyDocs/taskmaster/`, with a Python 3.11+ core/CLI and narrow consumer adapters. It reads configured evidence and writes its own derived export. There is no new daemon, database, scheduler, messaging producer, or execution authority. Manual refresh is sufficient for the pilot.

Autowork owns assignments, dispatch and outcome evidence. LIR is Lugos's thread-resumption protocol; OGMI stores its thread records and relationships; Torc owns lineage and accepted checkpoints. Taskmaster creates none of those authoritative records. It does not infer completion, acceptance, permissions, or objective membership from similar prose, a matching task hash, a notification, or a referenced ID alone.

First-release link coverage is deliberately bounded: explicit objective membership, ordinary Autowork run/outcome/assignment evidence, available current-policy bindings, and explicit chip annotations. Cross-review manifest adapters, historical-policy search, exact audit verification, new owner fields, and remote LIR/Torc adapters are later work. Report their coverage as unsupported or candidate-only where explicit evidence exists; never invent links to improve counts.

“Board” means Agent Mail's bulletin board for this plan. It is not needed to deliver any first-release consumer. The disabled Task Broker remains out of scope. No board posts, live migrations, global skill installation, automatic work admission, or remote mutations are authorized by this document.

## 2. Identity and explicit membership

An objective is `(namespace, id)`. Namespace identifies an explicitly configured objective source, not a guessed path. A record reference is `(owner, store_id, kind, id)`. `store_id` is a stable configured source alias, globally unique across owners; full host paths stay private. For a chip, store_id maps one-to-one to Dias project_id and id is chip_id; for a revision, store_id maps one-to-one to repository identity and id is the recorded revision. Reject duplicate aliases for the same project/repository. v1 kinds are `objective`, `run`, `assignment`, `policy`, `chip`, `revision`, and `audit_receipt`. No string-delimiter encoding is used for compound identities.

IDs are JSON strings containing valid Unicode scalar values. Preserve decoded string content exactly: no trimming, case folding, or Unicode normalization. Reject empty IDs, invalid UTF-8, unpaired surrogates, Unicode category Cc (including C1 controls), or IDs above 512 UTF-8 bytes with a typed configuration/input error; never truncate an identity. Render category Cf format characters, including bidi and zero-width controls, as visible Unicode escapes on all human-facing surfaces; keep the underlying identity unchanged. Apply the same display escaping to safe labels. Existing legacy IDs remain valid without adopting another owner's identifier grammar. Use separate CLI flags: `show --namespace VALUE --id VALUE --json`. IDs are never used as filenames.

Define canonical serialization `C(value)` as Python `json.dumps(value, sort_keys=True, ensure_ascii=True, allow_nan=False, separators=(',', ':')).encode('ascii')`. Its permitted domain has fixed ASCII schema keys; scalar Unicode strings; booleans/null; and integers in the interoperable range `[-(2^53-1), 2^53-1]`. Floats are excluded. Type validation distinguishes booleans from integer counters. Do not add numeric duration/usage projections to v1; retain their authoritative owner reference. Canonical test vectors freeze escaping, astral characters, integers, and array ordering. An objective's `objective_key` is lowercase SHA-256 of `C([namespace,id])`. Check uniqueness of both the original tuple and its key; a collision fails validation.

Taskmaster configuration declares each objective's `(namespace,id)`, annotation locator, and one run store independently of annotation-file readability. The initial annotation uses Autowork's existing `{objective_id, run_ids}` format. Its `objective_id` must exactly equal the configured id; disagreement produces `annotation_identity_mismatch`, a required-source failure for that objective. An unreadable or malformed annotation is also a per-objective required-source failure, with normal retention under section 4. A bare `run_id` is looked up only in the configured store; missing IDs produce `not_in_configured_store`. Do not search another store for a substitute. Several objectives may use different stores; multi-store membership within one objective is deferred until an explicit per-run binding contract exists. Duplicate IDs within a store are ambiguous input and fail the affected objective's refresh.

Membership is labelled `operator_annotated`; a future owner-written binding is separately labelled `owner_recorded`. If both disagree, export a `conflict` relationship when the inputs themselves remain structurally valid. Do not silently pick a winner. `resolved` membership means the stated annotation was verified against its source, not owner attestation that the run belongs to the objective.

Taskmaster configuration also owns mappings from `(project_id, chip_id)` to an objective. In v1 one chip may map to at most one objective, and an objective may map to several chips. Conflicting mappings are configuration errors. Export the mapping as a hashed `annotates_chip` link with `operator_annotated` provenance. This proves the annotation exists; it makes no claim that the chip currently exists in Dias. All consumers show `chip_existence_unchecked` for that separate question. Dias may attach the annotation to an exact matching current chip; otherwise it shows a local `chip_not_found` presentation note. That local note is explicitly separate from the shared trail and never changes its counts or digest. Never reuse Dias `linkedRunIds` for Autowork IDs or match chip titles.

## 3. One bounded export and exact hash semantics

Use a single `export.json` per configured output root. There are no generation directories, external index, or current-generation pointer. Retention of historic runtime exports is deferred; reviewed plans and fixture evidence remain separately archived.

The closed outer schema is `taskmaster.export/v1`, with `schema_version: 1`, `snapshot_id`, `published_at`, `max_age_seconds`, and an `entries` array. Each entry contains its objective tuple/key, nullable `content_json`/`trail_sha256`, and `observation`. The writer creates `content_json` as a JSON string whose decoded value is the exact ASCII JSON text produced by `C(trail_content)`. `trail_sha256` is SHA-256 of those decoded ASCII bytes. Consumers hash the stored string bytes, then strictly parse them; they do not reserialize the full content to verify its digest. Only the small identity-array encoding described below must be reproduced across runtimes.

`trail_content` contains `schema_version: 1`, objective identity, sources, refs, links, gaps, and coverage. Source records include owner/store identity, adapter version, pinned owner schema/version, raw-byte input digests, and `source_mode: live|saved_snapshot`. Source mode is separate from coverage. Saved sources include their manifest's evidence capture time or null when unknown. Links include relation, typed endpoints, status, and source evidence. Status is `resolved`, `candidate`, `missing`, `unavailable`, `unsupported`, or `conflict`. v1 relations are `has_run`, `has_assignment`, `uses_policy`, `has_revision`, `has_audit_candidate`, and `annotates_chip`; the Cirra slice of the work-view concept adds `has_production_audit`, `observes_finding` and `has_audit_gate`. Gaps have a stable code and affected reference. Coverage reports `checked`, `unavailable`, or `unsupported`. Counts are derived from these arrays, never interpreted as work completion percentages.

Normalize set-like arrays by sorting their canonical encoded semantic keys: sources by `(owner,store_id)`, refs by the reference tuple, links by `(relation,from,to)`, gaps by `(code,affected_ref)`, and coverage by adapter identity. Coalesce identical entries; contradictory values under the same semantic key must become an explicit conflict or a typed input error, not order-dependent output. Evidence arrays sort by `(source_ref,json_pointer,raw_sha256)`, where source_ref is exactly `(owner,store_id,record_type,record_id)`; ordered owner sequences are not copied into these sets. Outer entries, report rows, and the Dias default objective list sort by objective_key with no duplicates. Freeze the relation-specific field allowlist and full typed gap-code table in Batch 1. Unsupported relations are not silently dropped.

`snapshot_id` hashes `C([[objective_key,trail_sha256_or_null],...])`, sorted by objective key. It identifies the set of content observations, not a wall-clock publication event. Null content denotes a configured objective with no valid observation yet. Entry tuple/key and parsed content objective must agree; refs, links, and gaps must pass uniqueness and endpoint checks. Full-file SHA-256 may be emitted by diagnostics as `file_sha256`, but is not embedded in its own file or used as content identity. Observation-only updates change file bytes while preserving snapshot/trail IDs.

All readers, including show, report, verify-export, and Dias, use the same acceptance rules. Reject duplicate JSON keys, invalid UTF-8, unpaired surrogates, excess bounds, and unexpected fields before use. This applies both to the outer object and decoded content. Decoded content_json must consist entirely of printable ASCII bytes 0x20–0x7e before hashing. Validate number lexemes before numeric conversion: reject fractions, exponents, -0, and integers outside the permitted range. JavaScript's default JSON parser alone is insufficient; use a vetted strict parser or a small validation pass tested against the same fixtures. Every reader verifies the raw content hash, recomputes objective_key and snapshot_id, checks tuple/content agreement, and applies the same schema, ordering, uniqueness, endpoint, and observation invariants.

For the two identity hashes, implement only C's subset for arrays containing arrays, strings, and null: no whitespace; literal null; quote/backslash escapes; Python-compatible short escapes for backspace, tab, LF, form feed and CR; lowercase `\uXXXX` for other controls and every code point outside 0x20–0x7e; UTF-16 surrogate-pair escapes for astral code points; no slash escape. Shared vectors include DEL, C1, non-ASCII, astral characters, quote/backslash, empty arrays and null hashes. Identity validation still rejects controls in IDs. Wrong objective_key or snapshot_id is invalid_export on every surface.

Canonical full-content serialization is a writer obligation for newly generated content, asserted before publication and in writer fixtures. It is not an extra Python reader acceptance rule: all readers accept a non-canonical but hash-consistent content string if it satisfies every other rule (for example, different object-key order or extra ASCII spaces). They preserve those exact bytes when retaining content; retained entries undergo the common reader checks, not the new-content canonical assertion. No reader recanonicalizes it or silently repairs hashes. Shared fixtures prove identical acceptance of that case and identical rejection of wrong identity hashes. Raw hashes do not waive parsing checks. Hashes detect accidental corruption/inconsistent edits; an attacker able to rewrite all exported bytes and hashes is outside the pilot threat model. Signing is out of scope.

Closed v1 schemas reject unknown fields, enum values, relation types, and versions with `unsupported_export` or `invalid_export` as appropriate. Any field or enum addition needs a new schema version and coordinated readers; do not silently extend v1 in the later owner-link batch. No reader silently downgrades. Local diagnostics retain the exact validation reason, while the shared UI emits bounded typed errors.

Bounds: 8 MiB outer file, 64 objectives, 64 KiB decoded content per objective, 2,048 refs, 4,096 links, 4,096 gaps, 32 sources/coverage records per objective, 512-byte identities, 128-byte version/code tokens, 160-byte safe labels, and 1,280-byte JSON Pointers. Additionally cap each fully escaped outer entry at 96 KiB: accept content only if its encoded entry with null observation fits 80 KiB, reserving 16 KiB for observation and framing. The encoded-entry byte budget is the effective capacity limit; count limits are defensive parser ceilings, not a promise that that many records fit. Validate at configuration load that the maximum source-status frame fits that reserve; diagnostic detail never enters it. Non-entry envelope/framing overhead is capped at 16 KiB. Thus 64 bounded entries plus overhead fit below 8 MiB. A per-objective bound failure retains that objective's prior content under the usual binding rules and publishes `over_bounds`/failed metadata, or null content on its first attempt. It cannot consume other objectives' budgets. A fixture with decoded content below 64 KiB but escaped entry above 80 KiB must fail only that objective. A corrupt prior export or invalid global configuration remains a whole-command error. Never silently truncate. A display may paginate but must show full counts. Memory and decoder allocations are capped before parsing nested content.

## 4. Refresh, partial failure, and freshness

Observation metadata lives beside the immutable content string **inside the same replaceable export file**. It is excluded from trail/snapshot hashes. Per entry it includes `content_generated_at`, `last_attempt_at`, `last_success_at`, `has_successful_observation`, `attempt_status`, `error_codes`, `binding_sha256`, and per-source `last_checked_at`/health. All times are UTC RFC 3339. `content_generated_at` changes only when trail content changes; initial absent values are null. `has_successful_observation` is true exactly when valid content exists for the current binding, even if its evidence capture time is unknown; it becomes true after a successful or partial observation and stays true on retained-content failures. Null content requires this marker false, null trail hash/generated time/last_success_at, and a failed attempt. Root `published_at` changes on each successful file replacement, including status-only updates. The pilot maximum age is 86,400 seconds and is carried in the file for every consumer.

Only currently configured objectives appear in a newly published export; removed objectives disappear, and renaming the namespace/ID creates a new identity. Retention requires the same binding_sha256: a hash of the normalized non-secret configuration that binds the configured objective identity, annotation locator, run-store/source locators and aliases, source mode/requiredness, chip mappings, and safe presentation inputs. Compute it without reading the annotation or other owner evidence. Raw annotation bytes/digests and run membership are evidence, not configuration-binding inputs; the annotation digest belongs in trail_content source evidence after a successful read. Private locators participate only in the binding digest, never as exported strings; credential values are excluded. A changed binding followed by a failed attempt emits null content and `config_changed` alongside the underlying typed reason instead of retaining evidence from a different configuration. An initial failure with no prior entry does not imply config_changed. A successful or partial attempt replaces the binding normally. Configuration parse errors that prevent identifying objectives are command-level errors before publication.

An unreadable, malformed, or identity-mismatched annotation retains prior content when the configured binding matches and does not prevent other objectives publishing. Editing run_ids in that file followed by a required Autowork read failure likewise retains prior content without config_changed; it remains visibly failed/stale evidence from the prior successful observation. Changing the configured annotation locator is a binding change. Batch 1 fixtures cover each case, including annotation_identity_mismatch.

Each configured objective requires its annotation/configuration and the ordinary Autowork projection. Optional configured sources may include current policy evidence; deferred unconfigured adapters are explicitly unsupported coverage and do not block refresh. Source requiredness is configuration, with the required core sources enforced by schema. Do not silently reclassify a failing required source as optional.

| Observed condition | Publish behavior for that objective |
|---|---|
| Required reads succeed, ordinary run artifacts missing | Publish a new or unchanged valid trail with `missing` links/gaps supplied by the owner projection. A missing artifact is not a command failure. |
| Optional source absent/unreachable or its schema unsupported | Publish current required evidence, mark that optional coverage unavailable/unsupported, and mark its expected relationships unavailable/unsupported. Do not merge old resolved optional links into fresh content. Set `attempt_status: partial`. |
| Optional source has malformed/integrity-invalid data or duplicate identities | Discard evidence from that optional source, publish current required evidence as partial, and emit `optional_source_invalid` with unavailable coverage; private diagnostics retain the cause. Never keep its old resolved links. |
| Required source fails, required schema unsupported, malformed/integrity-invalid required records, unresolved required record identity, or per-objective over_bounds | Retain that entry's prior content/hash/generated time and successful-check times only if its configuration binding still matches; update attempt/error metadata with `attempt_status: failed`. Otherwise emit a null content entry. |
| Required inputs change during projection, still changing after one retry | Same failed-retention rule, with `source_changed_during_read`; do not label the source permanently corrupt. |
| Optional inputs change during projection, still changing after one retry, while required inputs are stable | Discard that optional source's evidence and old resolved links, publish current required evidence as partial with unavailable optional coverage, and record `source_changed_during_read` in its per-source health and entry error_codes. |
| Complete refresh with byte-identical content | Replace only observation values in the export; keep content bytes/hashes/generated time. |

Successful or partial refresh updates per-source checked times only for sources actually checked successfully. A live source uses its successful read time; a saved source uses its corpus manifest's recorded evidence capture time, never the time the copy was reread. Unknown capture time remains null and stale with `evidence_time_unknown`; do not derive it from filesystem mtime. `last_success_at` is the minimum checked time of required sources, or null if any required evidence time is unknown. It describes evidence age, not whether a successful observation ever occurred; the explicit marker answers that separate question. Reading an old corpus successfully can therefore still yield stale evidence. A failed objective retains its success marker, content and successful-check metadata only when the binding matches, even if one source was read during the failed attempt. Other objectives may publish successfully in the same outer file; each entry carries its own health. Every consumer prominently shows saved-snapshot mode. Counts and persisted error codes come from the saved entry, not independent consumer re-reading of owner stores.

`error_codes` replaces the single error_code with a duplicate-free, ASCII-sorted set of closed enum values (maximum 32 per entry; maximum 8 per source). Batch 1 freezes the enum table and verifies its worst-case frame fits the observation reserve; no prose or arbitrary error strings enter these arrays. On each attempt replace attempt-related codes, union all applicable source failure codes, and add config_changed when applicable. Include evidence_time_unknown whenever retained or newly published content has an unknown required evidence time. This preserves simultaneous conditions without precedence or historical-code accumulation. Per-source health distinguishes the latest attempt outcome from retained successful-check times. A failed attempt takes precedence over partial in attempt_status, but does not suppress applicable codes; partial means required inputs succeeded and at least one configured optional input did not. Unconfigured unsupported adapters alone do not make an attempt partial.

At a supplied `now`, `age_seconds=max(0, now-last_success_at)` when that time is known, otherwise null. `never_successful` means has_successful_observation is false, not last_success_at is null. `clock_skew` is true if any retained/current required-source successful-check time is later than now, even when another required time is unknown. `stale` is true if never_successful, last_success_at is unknown, the latest attempt failed, clock_skew is true, or age exceeds max_age_seconds. Partial optional coverage is separately visible and does not by itself make fresh required evidence stale. The read model exposes `status_codes`, the sorted union of persisted error_codes and clock_skew when applicable (maximum 33); time-relative codes are computed at the injected clock, not written back into the export. Consumers display all codes and the same stale/partial flags. Tests inject the same now; live surfaces opened at different times may legitimately cross the age threshold.

If publication itself fails, the on-disk export remains wholly unchanged. `refresh` returns a typed failure to its caller and records host-private diagnostics. Consumers cannot claim to know an unpublished attempt; they continue to show the prior entry's check time and age. This limitation is explicit rather than inventing a separate loosely coordinated status file.

Before and after projection, enumerate/hash the bounded allowlisted read set, including record existence, run-location ambiguity, and referenced probe dependencies used by Autowork. Scope discovery to configured run roots, never the MyDocs workspace. Batch 1 must document the exact owner read footprint and prove the adapter tracks it, including dependencies outside selected runs. If that cannot be bounded safely, use an explicit saved corpus for the pilot with source_mode `saved_snapshot` and its original evidence time; do not claim a stable live-store snapshot. Retry once on differences. This catches ordinary concurrent writes, not adversarial transactional races.

An active objective may remain stale while its required inputs continually change; that honest result is acceptable. Optional-only churn produces partial coverage instead. Neither prevents other objectives refreshing. No watcher or unbounded retry loop is added.

## 5. Windows-safe publication and recovery

The entire outer bundle, including retained entries and fresh metadata, is serialized and validated before publication. Write a uniquely named temporary file in the output directory, flush it, and atomically replace `export.json` on the same filesystem. Do not truncate the live file first. Process-interruption consistency is required; survival of abrupt power loss is not promised.

Acquire a nonblocking OS-held exclusive writer lock before reading the old export or beginning refresh. On Windows use a held byte-range lock in a persistent lock file; on macOS/Linux use the platform OS-held lock through a narrow adapter. File existence does not mean locked. Process death releases ownership; a second writer returns `busy` without changing the export. Never remove another process's lock file to recover.

Readers open/read bounded bytes/close immediately, then validate from memory. Use read/write/delete sharing where the runtime supports it. On sharing/access-denied read failures make at most three attempts with 50/100 ms delays; persistent failure is `export_unreadable` (exit 8), not missing. Only a confirmed absent file maps to exit 3. On Windows, sharing violations during replace trigger at most five attempts with 100/200/400/800 ms delays between attempts. If they persist, return `publication_failed`; leave the previous export and record diagnostics. The release gate exercises the actual chosen runtime and lock mechanism, including a reader that holds a conflicting handle. Do not assume Unix rename behavior establishes Windows correctness.

Unique abandoned temporary files are ignored by readers and never auto-promoted. Cleanup is separate, permission-governed housekeeping. A corrupt previous export is not silently overwritten: fail with `existing_export_invalid` (exit 4). The explicit recovery action is `refresh --recover-invalid-export`: under the writer lock, copy the invalid bytes to a unique timestamped `.invalid` sibling without overwriting, verify that copy, rebuild with no prior content, and replace the export only after full validation. Abort if preservation fails. No deletion or extra confirmation is needed when this recovery has already been authorized. An unsupported newer schema always returns exit 4 without mutation, even with the recovery flag. With no existing export, failed objectives may still be represented as null entries, so all consumers can show a precise first-run failure.

## 6. Owner adapters, privacy, and later links

Invoke the configured executable with an argument array for `autowork campaign outcome --runs-root PATH --objective FILE --json`. Pin its tool version and currently documented output `schema_version: 1`. An unknown version is a required-source failure. Use its launch/delivery/acceptance distinctions rather than re-deriving success. Batch 1 freezes an allowlist of extracted owner fields and verifies the output twice over unchanged fixtures. Observation fields in CLI stdout are not raw input digests in hashed trail content: use the actual owner artifact digests and the allowlisted semantic fields. Owner-recorded timestamps remain evidence; only Taskmaster observation timestamps are excluded from content identity.

Read only configured roots and declared record types. Reject traversal and symlink/reparse escapes. Do not open transcripts, credentials, child output, or arbitrary private documents. Shared evidence has source_ref `(owner,store_id,record_type,record_id)` plus json_pointer and raw_sha256, with no filesystem path; these are the same fields used for evidence sorting. Asserted values are schema-allowlisted IDs, hashes, enums, versions, booleans, or bounded integers. Unallowlisted fields are omitted entirely, not copied as arbitrary text. Preserve safe labels only from explicit presentation configuration; escape them as text, never HTML or executable markup. Raw paths and detailed errors stay in host-private diagnostics.

First-release audits remain candidate-only: an explicitly available repository/revision pair may identify a receipt candidate, never prove that the run was audited. Future exact resolution must compare independently recorded execution/artifact subject evidence to the full receipt subject and use the owner's pinned offline validator. A receipt's own digest cannot establish its match to a run. Missing required subject data yields `audit_subject_incomplete`; unavailable validator yields `validator_unavailable`. Keep input and output revisions distinct, preserve owner receipt status, and compute no replacement authority digest in Taskmaster.

Historical policy resolution is deferred. The initial adapter compares current file bytes only to recorded raw-byte hashes; no match is an explicit historical-lookup gap. A later historical adapter must use `git` blob bytes exactly, a declared repository and at most 256 configured candidate revisions. A missing match or EOL mismatch remains unresolved; normalized comparison is not needed. Its acceptance requires a guaranteed synthetic historical match and a missing-history fixture, never an optional “when available” test.

Later owner fields require separate versioned changes. WEIR is Lugos's web-evidence owner; its sealed WorkContext binds objective/run/assignment identity and a canonical hash. A root scope envelope records the root orchestrator's permitted task scope; its reference is supplied and validated, not inferred from a child hash. Preserve frozen WorkContext schemas and existing Autowork write-path provenance. These are later compatibility concerns, not first-release prerequisites.

## 7. All three consumer surfaces

**Agents.** Proposed commands are `refresh`, `show --namespace VALUE --id VALUE --json`, `show --all --json`, `show --all --format report`, and `verify-export`. All reads use the saved export; none implicitly refreshes. Define `taskmaster.show/v1` as a closed read-model schema containing objective identity, parsed nullable content, snapshot/trail IDs, observation, the evaluation time, and computed age_seconds/stale/clock_skew/never_successful/partial/status_codes/source mode. Partial is true exactly when attempt_status is partial; coverage details remain available even on failed retained entries. A shared `--now RFC3339` option on show/report and an injected clock in the Dias adapter make comparisons reproducible; the supplied evaluation time is included in output. `show` emits data with exit 0 for any schema-valid entry, including conflict links, stale data, partial coverage, or a null-content failed entry.

Codes are: 2 invalid arguments/configuration; 3 missing export/objective on reads; 4 invalid/unsupported/over-bounds export or invalid prior export; 5 refresh published with at least one failed objective, including per-objective over_bounds; 6 writer busy; 7 publication failure; 8 export unreadable. Refresh checks in order: configuration (2), lock (6), old-export read (8) and validation (4), build/publication (7), then failed-objective result (5) or success/partial-optional (0). It emits per-objective statuses on code 5. Missing prior export is allowed for refresh. `verify-export` checks validity/integrity, not completeness or freshness, and returns 0 for valid gapped data.

**Morning report.** Implement a deterministic renderer `show --all --format report`, backed by taskmaster.show/v1. It emits a fixed block with objective identities, snapshot/trail IDs, status counts, gap codes, checked times, maximum age, evaluation time, and stale/partial/status_codes. No narrative model decides counts or edits that block. For each report the helper captures one explicit now, invokes the renderer exactly once with `--now`, and retains its exact stdout byte buffer. The renderer validates one in-memory export read and emits UTF-8 with LF using binary stdout. The helper splices that buffer programmatically between fixed BEGIN/END markers and adds SHA-256 of the exact block bytes, excluding the markers/digest line. Write the report artifact in binary mode with no newline translation. The pre-delivery check requires exactly one delimited block, compares its exact bytes to the retained buffer, and verifies its digest; it never rereads export.json or reruns the renderer. A concurrent refresh cannot change the report being verified, whose snapshot and evaluation time remain explicit.

Modified, omitted, duplicate or malformed blocks fail that check and are replaced by a single typed error line; no unverified trail summary is delivered. CRLF translation inside the block is a deterministic verification failure, not silently normalized. A failed check is handled against the same retained buffer, not a new rendering. All subprocess launch failures and nonzero renderer exits map to one bounded status line while inbox processing continues. Tests check the final delivered report artifact, including corruption, omission, duplicate blocks, a refresh between insertion and verification, and Windows CRLF translation, not merely the renderer. Surrounding commentary does not authorize actions from gaps.

When Taskmaster is unconfigured, preserve today's inbox behavior including the early return. A configured Taskmaster export is read before the empty-inbox return. Missing, invalid, unsupported or unreadable exports produce one bounded status line and do not stop inbox handling. An invalid new export is not called current; consumers may retain a last validated in-memory view labelled stale/invalid-source, or show the status alone when no cached view exists. No new inbox items, archival policy, schedule, or board posts are introduced. Repository instructions are edited in their source location; any later global installation remains separately scoped.

**Dias.** A host-side adapter reads the configured export, validates the same schemas/hashes/bounds, and supplies a safe bounded display model. It does not run owner commands, browse owner files, or grant authority. Render an objective list and details, shared link/gap counts and freshness, plus explicit chip annotations. Missing chip presentation follows section 2. Include unavailable, unsupported, conflict, null-content, stale, and partial states. On invalid input retain only a visibly stale last validated view; on first load show the typed error. Paginated lists retain full totals. The browser simulator must continue to work.

Freeze Dias's actual active host/runtime from its current Phase 1H implementation before Batch 2; no parallel host stack is introduced. Dias intentionally reads the file independently so display consumption requires no Python installation or child-process launch. Its adapter uses shared byte/hash/parser conformance fixtures; invoking the CLI is an alternative, not a hidden requirement. Consumer-agreement tests compare taskmaster.show/v1-equivalent fields and a fixed clock, not prose layout, local chip existence, or human viewing times.

## 9. Deferred board and operational boundaries

The first proposal's nullable `kind`, `subject`, `source_ref`, and `idempotency_key` fields remain a design option. Producers must supply stable keys; duplicate payloads return the original post without repeated notification, while same-key/different-payload requests conflict. Filters must preserve existing global archival/reason requirements. Structured filters alone do not replace the HUD's emoji status classification. Test old clients and concurrent writers before any rollout.

Before migration execution, follow the global approval rule, including any disposable migration rehearsal. Before live rollout prepare the exact target, backup/restore approach, compatible artifact, and rollback, then obtain objective-scoped authorization. Prefer compatible additive rollback; restoring an older backup over newer posts requires explicit data-loss approval. Remote hosting, automatic refresh scheduling, and remote repository destination/visibility remain separate decisions. Batches 1 and 2 have since landed; the next implementation action is Batch 3, which still needs explicit authorization.
